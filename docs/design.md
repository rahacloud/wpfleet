# wpfleet design

wpfleet manages a fleet of WordPress sites on Kubernetes: one Helm release per site per environment, from values files kept in Git. It grew out of a real migration of two dozen sites, where every step below was first a shell script. This file is the contract that the packages are built against; change it in the same commit as the code that changes the contract.

## What a fleet is

A fleet is a Git repository that holds `wpfleet.yaml` at its root and one values directory per environment:

```text
fleet/
├── wpfleet.yaml
└── environments/
    ├── development/
    │   ├── _shared.yaml      # values every site in the environment shares
    │   └── blog.yaml         # one file per site; the file name is the site name
    ├── staging/
    └── production/
```

A release is rendered from the chart with `_shared.yaml` first and the site file second, the way `helm -f _shared.yaml -f blog.yaml` does. The release name is the site name; each environment lives in its own namespace, so the names do not collide. Site files may hold secrets (the database password and the WordPress salts); the fleet repository is expected to be private, and wpfleet never prints those values.

`wpfleet.yaml`:

```yaml
# The chart: empty uses the one embedded in the binary (charts/wordpress).
chart: ""
registry: registry.example.com/sites      # images are <registry>/<site>:<tag>
build:
  base: docker.io/library/wordpress:7.0.2-php8.4-apache
wpcli:
  # Copied into the pod when a command needs wp-cli; pods often have no egress.
  url: https://github.com/wp-cli/wp-cli/releases/download/v2.12.0/wp-cli-2.12.0.phar
  # The published SHA-512 of that phar is the default; a phar that does not
  # match is refused, and so is an empty sha512 unless allowUnverified is set.
  sha512: be928f6b8ca1e8dfb9d2f4b75a13aa4aee0896f8a9a0a1c45cd5d2c98605e6172e6d014dda2e27f88c98befc16c040cbb2bd1bfa121510ea5cdf5f6a30fe8832
  allowUnverified: false
environments:
  - name: development
    namespace: wp-development
    kubeconfig: ""                         # empty: the usual KUBECONFIG rules
    context: ""
    values: environments/development       # default environments/<name>
  - name: staging
    namespace: wp-staging
    promoteFrom: development
  - name: production
    namespace: wp-production
    promoteFrom: staging
    label:                                 # how the web UI names it; optional, the name otherwise
      en: Live site
      fa: سایت اصلی
backup:
  s3:
    endpoint: https://s3.example.com
    bucket: wordpress-backups
    region: ""
    # Keys come from WPFLEET_S3_ACCESS_KEY_ID and WPFLEET_S3_SECRET_ACCESS_KEY,
    # never from this file.
```

Configuration loads with koanf: defaults, then `wpfleet.yaml`, then environment variables with the prefix `WPFLEET_` (`__` separates levels), then flags.

## Commands

Global flags: `--fleet, -f` (the fleet directory, default `.`, env `WPFLEET_FLEET`), `--env, -e` (the environment, env `WPFLEET_ENV`), `--output, -o` (`table`, the default, or `json`, env `WPFLEET_OUTPUT`) and `--verbose, -v` (debug logs on stderr, env `WPFLEET_VERBOSE`). Output for people is a table; `--output json` gives JSON for scripts. A failing command prints `wpfleet: <error>` on stderr and exits 1; a command that needs another exit code without a message, like `diff`, returns `cli.Exit("", code)`. `wpfleet completion bash|zsh|fish` prints a shell completion script. `--help` or `-h` after any command, after a command's arguments too (`wpfleet sites show blog --help`), and `wpfleet help <command> [<subcommand>]` print that command's usage; urfave/cli v3 on its own read a leaf command's first argument as a subcommand to describe and failed with "No help topic", and its help command stopped at the first name, so `internal/cmd` gives every leaf command a `CommandNotFound` that prints its own help and the root a help command that follows every name. A name that is no command exits 3 with "No help topic for '<names>'".

| Command | What it does |
| --- | --- |
| `wpfleet sites list` | Every site of `--env`, or of every environment without it: site, environment, host, image, pod readiness, and in JSON the site's `url`. Host and image come from the values on top of the chart's defaults; READY is ready pods out of running ones. An environment whose cluster cannot be opened or read shows READY as `unknown` with a warning, and the rest still prints. |
| `wpfleet sites show <site>` | One site in one environment: host (and in JSON its `url`), image, release revision, pods, node, uploads volume and last backup. The last backup is the last successful run of the site's backup CronJob (`wpfleet backup list` reads S3). `--output json` gives one object. |
| `wpfleet deploy <site>... \| --all` | `helm upgrade --install` of each site, one after another. `--wait` waits for readiness. Never regenerates secrets. Records the fleet's commit in the release description (see "Git stays the source of truth"). A failing site does not stop the others: the result table shows it, and the command then fails naming every failed site. |
| `wpfleet diff <site>... \| --all` | What a deploy would change: the live manifest against the rendered one, hooks left out, blank lines and document order ignored, as a unified diff (`--output json`: one object per site). A site without a release diffs against nothing. Values under a Secret's `data` and `stringData` print as `(redacted <tag>)`, an HMAC under a key made for each run, so a changed secret shows without being printed. Exit code 1 when there is a difference. |
| `wpfleet build <site> --source <dir> [--tag T] [--set]` | Builds `<registry>/<site>:<tag>` from the site's code tree on `build.base` and pushes it. The context goes to `docker build` as a tar stream (BuildKit refuses file names that are not UTF-8): a generated Dockerfile (`FROM` the base, `COPY --chown=www-data:www-data site/ /var/www/html/`, OCI labels) and the tree under `site/`. Leaves out what holds the site's secrets or is written at run time: at the root, every file whose name starts with `wp-config` except `wp-config-sample.php` (so `wp-config.php.bak` and `wp-config-old.php` too) and every database dump (`*.sql`, `*.sql.gz` and the other compressions); `wp-content/uploads`, `wp-content/cache` and `wp-content/upgrade`; and at any depth `.git`, `.svn`, `.hg`, `.env`, `.env.*` and every `error_log`. `--set` writes the new image into the site file of `--env`, after the push succeeded; a site missing from `--env` fails before the build. Docker's output goes to stderr, so stdout keeps the result (site, image, file set). Default tag: UTC `YYYYMMDD-HHMMSS`. |
| `wpfleet promote <site>... --to <env>` | Copies `image.repository` and `image.tag` from the `promoteFrom` environment's site file into the target's, keeping comments and order. Only the two site files count: an image from `_shared.yaml` is not promoted, and a source site file without both keys is refused. Every site is planned before any file is written, so one refusal writes nothing; an unchanged site's file is not touched. Does not deploy; it prints `old -> new` per site. |
| `wpfleet admin <site> [--user L] [--open]` | Prints, and with `--open` opens (`xdg-open`, `open` or `rundll32`), a one-time login link to the site's admin, valid for 60 seconds. It logs in as `--user` (a login, email or ID), else the first super admin on a multisite, else the administrator with the lowest ID. `--output json` prints the URL, the user ID and the expiry. |
| `wpfleet backup run <site>` | Starts a Job from the site's backup CronJob, follows its logs, and fails when the Job fails. |
| `wpfleet backup list <site>` | The backups of a site in S3: stamp, database dump size, number of changed upload files, and when the CronJob expires the run by `backup.keepDays`. Needs the S3 keys in `WPFLEET_S3_ACCESS_KEY_ID` and `WPFLEET_S3_SECRET_ACCESS_KEY`. |
| `wpfleet backup restore <site> --stamp S [--uploads]` | Imports the dump from S3 into the site's database, and with `--uploads` syncs the uploads back, through a Job in the cluster (see below). `--stamp latest` takes the newest run. With `--uploads` the site must have a running pod, checked before anything is asked or created. Asks for confirmation unless `--yes`. |
| `wpfleet copy <site> --from <env> --to <env>` | Restores the source's latest backup, uploads included unless `--skip-uploads`, into the target, then moves the host with wp-cli `search-replace` and the page builder fix-up (see below). Refuses `--to production` unless `--yes-production`, checks that the target has a running pod before it overwrites anything, and asks for confirmation unless `--yes`. |

### Contracts between packages

- `fleet.Site` has `Name`, `Env` (an `Environment`) and `ValuesFiles []string` (shared first). `fleet.Host(values)` gives the canonical host from merged values exactly as the chart's `wordpress.hosts` helper does: the first of `domains`, else `<site><hostLabelSuffix>.<domainSuffix>`.
- `fleet.DiscoverSites(env, fileNames)` turns a listing of an environment's values directory into sites: every `*.yaml` except `_shared.yaml`, named by the file's stem, which must be a DNS label. `values.Sites(env)` reads the directory and calls it. `fleet.PlanPromotion(site, from, to, source, target)` compares the image of two site values and says what a promotion changes; `fleet.ParseImageRef` and `ImageRef.String` split and join `repository:tag@digest`. Domain code reads values through the small `fleet.Values` interface (`String`, `StringSlice`), which `values.Values` implements.
- `values.Load(files ...string) (Values, error)` merges like Helm (later files win, maps merge deeply, lists replace, an explicit null is kept for Helm). `Values` has `String(path)`, `StringSlice(path)`, `Bool(path)`, `Lookup(path)` and the generic `values.Get[T](v, path)`; paths are dot-separated. `values.SetImage(path, repository, tag string) error` edits one site file in place and keeps every comment, the key order and the rest of the file byte for byte; it adds a missing key or `image:` block, and refuses with `ErrUnsupportedLayout` a layout it cannot edit that way (a block scalar, an anchor, a flow mapping without the key) instead of rewriting the file. It is `values.PlanImage`, which computes the edit as an `ImageEdit` (`Path`, `Before`, `After`, `Changed()`) without writing, followed by `ImageEdit.Write()`, which refuses with `ErrChangedOnDisk` a file that changed since it was read; `promote` plans every edit before it writes one.
- `kube.Client` is made per environment with `kube.New(kube.TargetFor(env))` (kubeconfig, context, namespace; the usual loading rules when the kubeconfig is empty). Pods of a site are selected by `app.kubernetes.io/instance=<site>` and `app.kubernetes.io/component` not equal to `backup`. Commands depend on the interfaces, not the struct: `kube.Execer` (`Exec`, `CopyFile`), `kube.Pods` (`SitePods`, `RunningPod`), `kube.Jobs` (`JobFromCronJob`, `WaitJob`, `JobPods`, `StreamLogs`) and `kube.Interface`, which is all three plus `Namespace()`. `Exec` streams over WebSocket and falls back to SPDY, and refuses with `kube.ErrNoStreams` (`ExecRequest.Validate`) a command with none of stdin, stdout and stderr, which the kubelet refuses too; `kube.ExitCode(err)` reads a command's non-zero exit code. `CopyFile` copies into the `wordpress` container through `tar -x`. `kubetest.New(namespace, objects...)` gives a `kube.Interface` on the fake clientset whose exec records every call, refuses a call with no stream as the kubelet does, understands `tar -x`, `test -f` and `mv -f`, and hands other commands to a handler the test sets.
- `helm.LoadChart(path)` loads a chart directory or archive, or the embedded chart when the path is empty. `helm.New(chart, target)` gives a client with `Render(ctx, site, namespace, valuesFiles)` (client-side, like `helm template`, hooks left out), `UpgradeInstall(ctx, site, namespace, valuesFiles, helm.InstallOptions{Wait, Description})` (installs when there is no release or its newest revision by number was uninstalled with its history kept, else upgrades with the given values only; `Wait` waits for readiness, otherwise only for hooks; `Description` becomes the revision's description), `LiveManifest(site, namespace)` (the last deployed revision, the one the cluster runs, hooks left out; a release with no deployed revision is `ErrReleaseNotFound`) and `Status(site, namespace)` (revision, status, chart version, updated, and `Description`, which the CLI's JSON leaves out). A missing release is `helm.ErrReleaseNotFound`. Releases are stored in Secrets, as the helm CLI does, and applied with server-side apply under the helm CLI's field manager, `helm` (`helm.FieldManager`), so a release can move between wpfleet and `helm upgrade` in either direction; under two managers, a change to a field the other one owns fails as a conflict and leaves a failed revision.
- `wpcli.Ensure(ctx, wpcli.Source{URL, SHA512, AllowUnverified})` downloads the phar once into the user's cache (`wpfleet/` under `os.UserCacheDir()`) and checks its SHA-512 before the file enters the cache; a source without a sum is refused with `ErrNoChecksum` unless it allows an unverified phar. The cache entry is named after the sum, or after a hash of the URL when there is none, so a changed URL or sum never reuses another file. `wpcli.NewRunner(kube, phar)` returns a runner whose `Run(ctx, pod, stdout, stderr, args...)` and `Output(ctx, pod, args...)` copy the phar into the pod once and run `php <remote> --allow-root --path=/var/www/html <args>` in the `wordpress` container (`wpcli.Command(remote, args...)`). The remote path is `wpcli.RemotePath(sum)`, `/tmp/wp-cli-<first 32 hex digits of the local phar's SHA-512>.phar`, checked with `test -f`; the copy goes to a temporary name and is renamed into place with `mv -f`, so an interrupted copy or another phar is never run.
- `docker.New(runner, log)` builds and pushes through a `docker.Runner` (`Run(ctx, stdin, stdout, stderr, args...)`; `docker.CLI` runs the binary, tests use a fake). `Build(ctx, spec)` runs `docker build --tag <ref> -` with the context from `docker.WriteContext`, which writes the GNU tar format so names that are not UTF-8 stay byte for byte, keeps modes and symbolic links, and drops owners; `docker.Excluded(rel)` is the exclude rule. `Push(ctx, ref)` runs `docker push`.
- `Env.ChartValues(site)` gives a site's values over the chart's defaults, what the chart's templates see, and `ops.SiteURL(values)` the site's URL from them: the host as `fleet.Host` gives it, over HTTPS unless `ingress.tls.enabled` is false. `SiteRow.URL` and `SiteDetail.URL` carry it (empty without a host), so the UI links a site with the scheme its ingress serves. `admin` and `copy` take the host and the scheme from these, like `sites`, so a fleet's own chart with host defaults is followed.
- `ops.LoadFleet(dir)` loads `wpfleet.yaml`; `(*ops.Fleet).Open(name)` selects an environment, discovers its sites and makes its kube client without contacting the cluster. The returned `*ops.Env` has `Sites`, `Kube` (a `kube.Interface`, which a test replaces), `Site(name)`, `SelectSites(names, all)` (`ops.ErrNoSites`, `ops.ErrSitesAndAll`), `Values(site)`, `ChartValues(site)`, `Helm()` (loads the chart on first use) and, through the embedded `*ops.Fleet`, `Dir`, `Config`, `Fleet`, `Sites(env)`, `WPCLI(ctx, kube)` and `ChartPath()`. `cmdutil.Fleet` and `cmdutil.Env` are aliases of these; `cmdutil.LoadFleet(cmd)` and `cmdutil.OpenEnv(cmd)` read `--fleet` and `--env`. `cmdutil.Print(cmd, rows, columns...)` writes rows of any type as a table, or as JSON by their `json` tags with `--output json`.
- **Operations.** Each function of `internal/ops` takes the environment (or the fleet, for what spans environments), the sites and an options struct whose zero value uses the real dependencies (a nil `Releases`, `Cluster`, `Pods` or `WP` is the environment's own; tests pass fakes), returns typed results, and reports progress through an `ops.Progress` callback (`func(ops.Event)`): an `Event` has a `Kind` (`deploying`, `job-started`, `log`, `done`), `Env`, `Site`, `Job`, `Namespace` and `Text`, which for `log` is a chunk of a Job's logs and otherwise the English line the CLI prints. Events come in order from one goroutine at a time; `cmdutil.ProgressTo(cmd)` prints logs on stdout and the other lines on stderr, exactly as the commands did before. Nothing in ops prints, asks a question or reads a flag.
- `ops.Deploy(ctx, env, sites, DeployOptions{Wait, Releases, Commit}, progress)` returns a `DeployReport` (`Results []DeployResult`, `Commit`, `Failed`; `Err()` wraps `ops.ErrSitesFailed`); its own error is only for a missing Helm client or the context ending between sites. Every deploy records `Commit.Description()` as the release description: `wpfleet <sha>`, `wpfleet <sha>-dirty`, or `wpfleet` outside Git. `ops.FleetCommit(dir)` reads it with go-git, so no git binary is needed: HEAD's full SHA, dirty when anything under the fleet directory (untracked files included, ignored ones not, the user's `core.excludesFile` honoured) differs from it. A nil `Commit` option reads it; the server passes its clone's head. `ops.ParseDescription` reads it back. `ops.Diff(ctx, env, sites, DiffOptions{Releases})` returns a `DiffReport` (`Diffs []SiteDiff`, `Failed`, `Err()`, `Changed()`).
- `ops.PlanPromotion(fleet, to, names)` returns a `Promotion` (`To`, `From`, `Plans`, `Files()`, `Changed()`) without writing; `ops.ApplyPromotion(ctx, promotion)` writes it and returns one `PromoteResult` per site (`fleet.PromotionPlan`, `Changed`, `File`), refusing with `values.ErrChangedOnDisk` a file changed since the plan. The server commits `Files()` and, when its push is refused, resets and plans again.
- `ops.AdminLogin(ctx, env, site, AdminOptions{User, MatchEmail, Pods, WP, Random})` returns a `Login` (`URL`, `UserID`, `Expires`, `MatchedEmail`, the last left out of JSON). With `MatchEmail` and no `User` it looks the email up with `wp user get <email> --field=ID` and logs in as that user when `wp eval` finds the role `administrator` or a super admin; any failure falls back to the CLI's choice. `ops.IssueLogin(ctx, wp, LoginRequest, random)` is the step that stores the token; `ops.WP` is the wp-cli it needs, which `opstest.WP` fakes.
- `ops.ListSites(ctx, fleet, envs, ListOptions{Cluster})` returns `[]SiteRow`; `ops.ShowSite(ctx, env, site, ShowOptions{Cluster, Releases})` returns a `SiteDetail` (`URL`, `Release`, `Pods []SitePod`, `Volume SiteVolume`, `Backup SiteBackup`). `ops.Cluster` is `kube.Pods` plus `Clientset()`, `ops.ReleaseStatus` is `Status`.
- `ops.History(ctx, env, site, n, HistoryOptions{Releases, Authors})` returns the newest `n` revisions of a site's release, newest first, as `[]Revision` (`Revision`, `Updated`, `Status`, `ChartVersion`, `Commit` read by `ParseDescription`, zero for a revision wpfleet did not deploy, and `Author`, the Git author of that commit); a site without a release has none and no error. `ops.ReleaseHistory` is `helm.Client.History(site, namespace, max)`, which sorts by revision number since the Secret driver lists `v10` before `v9`. `ops.CommitAuthors` is `CommitAuthor(ctx, sha)`; the server passes its clone, and a nil one looks in the Git repository that holds the fleet directory, as `FleetCommit` does. Each commit is looked up once per call, and a commit the repository does not have (deployed from another branch, or from a CLI's unpushed tree) only leaves `Author` empty.
- `ops.RunBackup(ctx, env, site, BackupOptions{Now, Poll, Getenv}, progress)` returns the `BackupRun` (`Job`, `Namespace`); `ops.ListBackups` returns `[]BackupRow` (the run and its `Expires`). A restore is two steps so a caller can ask between them: `ops.PlanRestore(ctx, env, site, RestoreOptions{BackupOptions, Stamp, Uploads})` returns the `RestoreSpec` without creating anything (and with uploads checks the site's running pod), `ops.DescribeRestore(spec)` says in English lines what it will do, and `ops.Restore(ctx, env, spec, opts, progress)` creates the Job and follows it. `copy` builds its spec with `ops.NewRestoreSpec` and runs it with `ops.Restore`.
- `ops.Locks` lets one operation run per site and environment, except those its `Beside(running, wanted)` rule lets run together: `TryLock(env, site, action)` returns a release function, or a `*ops.BusyError` (wrapping `ops.ErrBusy`) naming an action holding the site that the rule does not allow beside this one; `Running(env, site)` reports the action that took the site first, and `Blocking(env, site, action)` the one that would refuse `action` now, so a page can say why before anyone presses the button. A release removes only its own entry. The zero value is ready and, with a nil `Beside`, allows nothing together; the locks are in memory, which is why the server runs one replica.
- `backup.ParseStamp` and `Stamp.String` read and write the CronJob's stamp (`date -u +%Y%m%dT%H%M%SZ`); `backup.Prefix(namespace, site)`, `DumpKey`, `CurrentKey` and `ChangedKey` give the keys of the bucket layout below. `backup.Merge` joins dumps and changed-upload counts into runs, newest first; `Latest` and `Find` pick a run, and `Expires` gives when the CronJob's retention deletes one. `backup.PlanRestore(prefix, runs, stamp, uploads)` gives a `RestorePlan`, and `backup.SiteOf(values)` derives the names a restore needs (Secret, claim, database, images) exactly as the chart's helpers do. `backup.JobName(base, now)` names a Job as `<base>-<stamp in lowercase>`, cut to 63 characters.
- `s3.New(s3.Config, s3.Credentials)` reads the bucket; `s3.CredentialsFromEnv(getenv)` takes the keys from `WPFLEET_S3_ACCESS_KEY_ID` and `WPFLEET_S3_SECRET_ACCESS_KEY` only. `Client.Backups(ctx, prefix)` lists `database/` and `uploads/changed/` under a site's prefix.
- `kube.JobCreator` (`CreateJob`) creates a Job built in Go; `kube.Client` implements it beside `kube.Interface`, so operations that need it get `Env.Kube` as an `ops.JobCluster` through `ops.JobClusterOf(env)`.
- Configuration: `WPFLEET_BACKUP__S3__BUCKET` sets `backup.s3.bucket`, and so on; a variable sets a key as the file and the defaults spell it, so `WPFLEET_SERVER__PUBLICURL` sets `server.publicURL`. `WPFLEET_FLEET`, `WPFLEET_ENV`, `WPFLEET_OUTPUT`, `WPFLEET_VERBOSE`, serve's `WPFLEET_CONFIG` and `WPFLEET_DATA`, the two S3 key variables and the five server secrets below are never read as configuration keys (`config.ReservedEnv`); a test checks that every flag's variable is among them. Validation requires unique, non-empty environment names, a namespace for each, and a `promoteFrom` that names another environment. `config.LoadFile(path, environ)` loads a file outside a fleet directory, as the server's ConfigMap mounts it.
- The server section: `Config.Validate` checks it only for what is wrong in any fleet (a negative duration; an access rule without a group, environments, sites or permissions, or naming an unknown environment), because the CLI never uses it; `Config.ValidateServer()` checks what `serve` needs on top (a listen address, `metricsListen` empty or another address, absolute `publicURL` and issuer, the repository URL and branch, a committer name and email, a client ID and groups claim, a positive poll interval and session length). `Server.RedirectURL()` is `<publicURL>/auth/callback`. The rules are `config.AccessRule` with plain strings; the permission names are checked by `access.Policy.Validate` when `serve` turns them into the policy. `config.ServerSecretsFromEnv(getenv)` reads `WPFLEET_OIDC_CLIENT_SECRET` (empty for a public client), `WPFLEET_SESSION_KEY` (required: 32 bytes in standard or URL-safe base64), `WPFLEET_GIT_SSH_KEY`, `WPFLEET_GIT_TOKEN` (not both) and `WPFLEET_GIT_WEBHOOK_SECRET` (empty refuses every webhook).
- `gitrepo.Open(ctx, gitrepo.Config{URL, Branch, Dir, SSHKeyFile, Token, Committer})` clones the fleet repository into an empty or missing `Dir` (one branch, no tags), or opens the clone there and refuses one of another remote with `gitrepo.ErrOtherRemote`, then syncs it. `Sync(ctx)` fetches the branch and hard-resets the clone to it, untracked files removed, and returns the head; `Head()` and `Dir()` read the clone. `Commit(ctx, msg, author, edit)` makes one change at a time: it syncs, runs `edit(dir)`, commits the paths it returns (absolute or relative; a deleted file is removed; a path outside the clone is `ErrOutsideClone`) with `author` (the committer when empty) and the bot committer, and pushes without force. When the push fails and a fetch shows that the branch moved, it syncs, runs `edit` again and pushes once more; a second refusal is `ErrPushRefused`. An edit that changes nothing is `ErrNothingToCommit`, and every failure leaves the clone reset to the remote. `FileLog(ctx, path, n)` gives the newest `n` commits that touched a file (`LogEntry{SHA, Author, Email, When, Subject}`), and `CommitAuthor(ctx, sha)` the author of one commit (`gitrepo.Author(repo, sha)` on any go-git repository), `ErrUnknownCommit` for one the clone does not have or a name that is not a full hash. `gitrepo.VerifyWebhook(secret, body, header)` checks an HMAC-SHA256 header, `sha256=<hex>` or bare hex, in constant time, and refuses everything without a secret. An SSH key's user is the URL's, else `git`, and host keys are checked against `SSH_KNOWN_HOSTS`, else `~/.ssh/known_hosts`, read when the auth is made, and the host is asked for exactly the key types listed for it there, so a file with only the host's ed25519 key works (go-git otherwise lets the host answer with the ECDSA key it prefers, and the check fails with a key mismatch); a token goes as HTTP basic auth with the URL's user, else `x-access-token`.

## The chart

`charts/wordpress` is the chart every release uses. Its `values.yaml` documents every value; `php.timezone` (default `UTC`) sets PHP's `date.timezone` and `backup.timeZone` (default `Etc/UTC`) the CronJob's schedule. Two parts of it exist for wpfleet's commands:

- **The backup CronJob** (`backup.enabled`): every night it dumps the database with the site's own user and copies the dump and the uploads to S3 with rclone, under `<namespace>/<site>/database/<stamp>.sql.gz`, `<namespace>/<site>/uploads/current/` and `<namespace>/<site>/uploads/changed/<stamp>/`. It mounts the site's uploads claim, so a required pod affinity (`kubernetes.io/hostname`, the site's pods without the backup component) puts it on the node of the site's pod: a ReadWriteOnce volume attaches to one node only. Runs older than `keepDays` are deleted by the stamp in their name. The keys come from a Secret in the namespace with `access-key-id` and `secret-access-key`.
- **The one-time login** (`wordpress.oneTimeLogin`, on by default): the must-use plugin `files/wpfleet-login.php`, put in the ConfigMap and mounted read-only at `wp-content/mu-plugins/wpfleet-login.php`. `wpfleet admin` makes a token of 32 random bytes in unpadded URL-safe base64 and stores, through `wp option add --format=json --autoload=no --url=<site URL>`, the option `_wpfleet_login_<sha256 of the token>` holding `{"hash", "user", "expires"}`, the expiry 60 seconds ahead by the site's clock, read first with `wp eval 'echo time();'`, so a wrong local clock cannot stretch a link's life. The token itself never reaches the site. The plugin answers `/?wpfleet-login=<token>` on `init`: it deletes the option before anything else, and only the request whose delete succeeds goes on, so a link works once even under a race; it then checks the hash with `hash_equals` and the expiry, which must not be past nor more than 70 seconds ahead (60, plus room for clocks between pods), sets the auth cookie, fires `wp_login` and redirects to `admin_url()`. A malformed, unknown, used or expired token falls through to the normal page. `--url` makes wp-cli write the option of the site that answers the link, which matters on a multisite network. Expired tokens that nobody used stay behind as options holding only a hash.

## Restoring a backup

`backup restore` and `copy` create a Job built in Go, not a chart template, in the target site's namespace. Its init container runs the chart's `backup.image` (rclone, configured like the CronJob's, with the keys from the namespace's `backup.s3.secretName`) and copies `<prefix>/database/<stamp>.sql.gz` into an `emptyDir`; with uploads it mounts the site's uploads claim, runs beside the site's pod through the same pod affinity as the CronJob, `rclone sync`s `uploads/current/` into it (leaving `lost+found` alone) and gives the files to `podSecurityContext.fsGroup`. Its main container runs `database.provision.image` and imports the dump as the site's own database user, with the password from the site's Secret. The values come from the site's files over the chart's defaults; the bucket is wpfleet.yaml's, the endpoint the site's `backup.s3.endpoint` when set (the cluster may reach S3 by another address), else wpfleet.yaml's. The Job does not retry and is deleted a week after it finishes; the command follows the logs of both containers and fails when the Job fails.

The mirror is as of the latest run. Restoring the uploads of an older run copies over the mirror what each later run replaced or deleted, newest first, which puts every file those runs touched back as it was; files first uploaded after that run stay, because the bucket does not record additions. `copy` always restores the latest run, so its uploads are exact. For `copy`, the target namespace's S3 secret must be able to read the source's prefix in the same bucket.

## Copying between environments

A host change needs more than `search-replace`. BeTheme keeps its page builder data base64-encoded in the post meta `mfn-page-items`, and WPML caches its switcher templates as objects of classes wp-cli does not load. `internal/infra/assets/rehost-extra.php` decodes and rewrites the first and deletes the second; `copy` runs it with `wp eval-file` after `search-replace "$old" "$new" --all-tables-with-prefix --skip-columns=guid --precise`. On a multisite it adds `--network` and `--url=<source URL>/`: the imported database still names the source's domain in `wp_blogs` and `wp_site` while the target's `DOMAIN_CURRENT_SITE` names its own, so wp-cli can only load the network by the source's URL until the domain is replaced. The source and target hosts come from each site's values over the chart's defaults. The fix-up's tests run it in PHP against stubbed WordPress functions.

## The server

`wpfleet serve` runs the same operations as the CLI behind a web UI, for people who sign in with single sign-on and have no kubeconfig. It runs as one Deployment inside the cluster it manages, in the client's cluster and never on ours, behind that cluster's ingress. It is the most powerful thing in those namespaces: it can deploy every site and log in to every site's admin. So access control, CSRF protection and an audit log are part of its first version, not later work.

### Git stays the source of truth

The server works on a clone of the fleet repository, not on files of its own. Every change of state is a commit: `promote` in the UI edits the site file as the CLI does, commits it with the signed-in person as the author and the server's bot identity as the committer, and pushes it to the configured branch. A deploy in the UI deploys what that branch holds at that moment, never an uncommitted file, so the cluster can always be explained by a commit. Every deploy, from the CLI too, stores the fleet's commit in the Helm release's description (`wpfleet <sha>`, with `-dirty` when the CLI deployed from a tree with uncommitted changes), so the UI shows which commit each site runs.

- **Pull:** the server fetches the branch every `server.git.pollInterval` (default 1 minute) and at once on a push webhook (`POST /hooks/git`, signed with HMAC-SHA256 by `WPFLEET_GIT_WEBHOOK_SECRET`, in the GitHub and Gitea header format). It hard-resets its clone to the remote; nobody edits that clone by hand.
- **Push:** one write at a time. When the push is refused because the branch moved, the server resets to the new remote head, plans the edit again, and pushes once more; a second refusal fails the action and changes nothing.
- **Auth:** an SSH deploy key (`WPFLEET_GIT_SSH_KEY`, a file path) or an HTTPS token (`WPFLEET_GIT_TOKEN`), never from `wpfleet.yaml`. A token is refused with a plain `http` URL, since basic auth would send it in clear text, except to a loopback host for local tests.
- **Not in the server's first version:** opening a pull request instead of pushing (each Git host has its own API), `build` (it needs a Docker daemon or an in-cluster builder) and `copy`.

### Single sign-on and access

Sign-in is OpenID Connect with any provider that publishes discovery (Keycloak, Dex, Azure AD, Google; GitHub through Dex): the authorization code flow with PKCE, `state` and `nonce`. The ID token's subject, email, name and groups claim (`server.oidc.groupsClaim`, default `groups`) are kept in the session; nothing else about the person is stored. The sign-in asks for the scopes `openid`, `email` and `profile`, and `groups` when the provider's discovery lists it in `scopes_supported`: Dex puts the groups claim in the ID token only for that scope, while Google refuses a scope it does not know. `server.oidc.scopes` replaces that choice for a provider that needs other scopes. An email the provider marks as not verified (`email_verified: false`) is dropped, so it never matches a WordPress user, and so is an email without `email_verified` at all: Azure AD never sends the claim and, in some tenants, lets people edit their email, so with `matchEmail` a person could set a colleague's address and be logged in to a site as that colleague's WordPress user, under that colleague's name in the site's records. `server.oidc.assumeEmailVerified` (off by default) keeps such an email, for a provider whose email claim people cannot change. The session is a cookie encrypted with AES-GCM under `WPFLEET_SESSION_KEY` (32 bytes, base64), `HttpOnly`, `Secure`, `SameSite=Lax`, and it ends after `server.session.maxAge` (default 8 hours), when the groups are read again at the next sign-in. Every request that changes something is a `POST` with a CSRF token bound to the session.

Access is denied unless a rule allows it. A rule names a group, the environments and the sites it covers (exact names or `*`), and the permissions it allows:

| Permission | Allows |
| --- | --- |
| `view` | the site in lists, its details, its diff, its history and its backups |
| `deploy` | `promote` into the environment, and `deploy` there |
| `login` | the one-time admin login |
| `backup` | `backup run` |
| `restore` | `backup restore`, which overwrites the site's database and, if asked, its uploads |

Every permission includes `view`. A person's permissions are the union of every rule that matches one of their groups; a person with none gets a page that says so and nothing else. `promote` checks `deploy` on the target environment and `view` on the source. The rules are evaluated by pure code in `internal/domain/access`, with a test for each row of the table.

The packages behind this, and what each one guarantees:

- `access.Policy{Rules}` is the `server.access` list. `Allows(groups, env, site, perm)` is false unless a rule for one of the groups covers the environment and the site and grants the permission or, for `view`, any permission; an unknown permission, an empty name and a person with no groups are always refused. `Permissions(groups, env, site)` lists what is allowed, `view` first, and `Any(groups)` says whether the person may see anything at all. `*` stands for a whole name only, and `Validate()` refuses a rule with no group, environment, site or permission, an unknown permission, a group pattern, or a `*` inside a name such as `shop-*`, every problem wrapping `access.ErrInvalidRule`. `access.Identity` (`Subject`, `Email`, `Name`, `Groups`) is the signed-in person.
- `audit.Record` (`Time`, `Actor`, `Action`, `Env`, `Site`, `Commit`, `Result`, `Detail`, `WPUser`, `Allowed`) becomes one line through `Attrs()`: `audit: true` first, the actor's subject, email and groups (not the name), the time as `at` because the handler writes its own `time`, and the optional fields only when they are set. The results are `audit.ResultOK`, `ResultDenied`, `ResultFailed`, `ResultBusy` and `ResultStarted`.
- `session.NewManager(key, maxAge, secure)` seals both cookies with AES-GCM under the 32-byte key (`session.DecodeKey` reads the base64 of `WPFLEET_SESSION_KEY`), each bound to its purpose so one cookie's value never opens as the other. The cookies are `HttpOnly`, `SameSite=Lax`, `Path=/` and, with `secure`, `Secure` and named with the `__Host-` prefix. `New(identity, lang)` gives a session with a fresh CSRF token that ends after `maxAge`; `Get` refuses a cookie that is missing, changed, expired, or would outlive a lowered `maxAge`; `Set` refuses one larger than 4096 bytes (`session.ErrTooLarge`) rather than let the browser drop it. `CheckCSRF(r, session)` compares the `X-CSRF-Token` header or, without it, the `csrf` form field of the body, in constant time; the query string is never read. `session.NewFlow(returnTo)` makes the sign-in's state, nonce and PKCE verifier, `SetFlow` and `TakeFlow` keep them, with the return path and the language picked before sign-in (`Flow.Lang`), in a second cookie for ten minutes and use it once, and `session.SafeReturnPath` keeps the return path to a path on the same site (no `//host`, back slashes, control characters or `/auth/` routes) so a sign-in cannot redirect elsewhere.
- `oidc.New(ctx, oidc.Config{Issuer, ClientID, ClientSecret, RedirectURL, GroupsClaim, Scopes})` reads discovery (empty `Scopes` are `oidc.DefaultScopes()` plus `oidc.GroupsScope` when discovery advertises it); `AuthURL(state, nonce, verifier)` is the code flow with the S256 challenge, and `Exchange(ctx, code, verifier, nonce)` returns the `access.Identity` after go-oidc has checked the signature, issuer, audience and expiry, and wpfleet the nonce, the subject and, for a token with several audiences, that `azp` is this client. The groups claim may be a list or a single string; a claim name with dots that is not a claim of its own is a path into nested objects (`realm_access.roles`). `internal/infra/oidc/oidctest` is a provider for tests with discovery, a JWKS, PKCE checks and switches that break the ID token on purpose.

### The admin login

"Open admin" in the UI makes the same one-time link as `wpfleet admin` and redirects the browser to it, so the link never shows on the screen. With `server.admin.matchEmail` (on by default) it logs in as the WordPress user whose email is the signed-in person's, when one exists and is an administrator, so the site's own records name the right person; otherwise it logs in as the CLI would. The audit record says which WordPress user it was. Making the link takes the site's lock, but beside other actions: the server's `ops.Locks` uses `web.Beside`, which lets a login run while a deploy, a publish, a backup or another login holds the site, and nothing run beside a restore. A login writes one short-lived option through wp-cli and reads nothing else; a deploy's new pod and a backup's dump do not mind it (a dump may hold the hash of a token that has long expired), while an editor waiting minutes for a deploy to open the admin would. A restore replaces the database the token is written into, so a login while one runs is refused as busy, and a restore waits for a login in progress. The pages say so before anyone presses the button: `SiteView.AdminBlockedBy` and `CardEnv.AdminBlockedBy` name the action that would refuse "Open admin" (only a restore), empty when it can open, and the home page and the site page then disable the button with a line that says why ("Restore is running on this site. The dashboard opens again when it ends.").

### Audit

Every action, allowed or refused, writes one JSON line to stdout with `"audit": true`, and so does every sign-in and sign-out: the time, the person's email and groups, the action, the environment and site, the commit (for promote and deploy), the result, and for a login the WordPress user. The cluster's log collection keeps them; the server keeps no database. Changes of state are in Git as well, so the history of a site file is the history of its promotions. The server also records a Kubernetes Event (`events.k8s.io/v1`, reporting controller `wpfleet`, the pod's name as the instance) on the site's Deployment for deploy, login, backup and restore, and for promote, which deploys, so `kubectl describe` shows them. Only an action that ran gets one: `Normal` with the reason `WpfleetDeploy` and the like when it succeeded, `Warning` with `WpfleetDeployFailed` when it failed; a refusal or a busy site changed nothing there and is in the audit line only. The Event is written in the background, so a slow API server never holds back a page, and a site without a Deployment gets none. Signing in is the action `sign-in`: `ok` with the person as the actor; `denied` with no actor when the provider refused, the callback's state was forged or used, or the code did not redeem; `denied` with the person when no access rule matches their groups, who then gets no session, only the page that says they have no access (`Authorizer.Any`); `failed` when the session could not be stored. Signing out is `sign-out`, `ok`, or `denied` for a missing CSRF token; a sign-out without a session changes nothing and writes no line. Neither names a site, so neither gets an Event. The audit results are `ok`, `denied`, `failed` and `busy` (`audit.Result*`), and the counter `wpfleet_actions_total` uses the same names, with `sign-in` and `sign-out` among its actions. An action that runs in the background (deploy, promote, backup, restore) writes a line with the result `started` and its task ID when it is accepted, before it touches anything, and a second line with `ok` or `failed` when it ends, so an action cut off by a killed pod is still in the log; `started` gets no Event and is not counted, so the counter counts each action once.

### The UI

The UI is for people who run a site's content, not its infrastructure: an editor or a marketing team signs in with the company account, sees only their sites, and opens each one's admin with one click, without a WordPress password. So each page leads with the action and says it in their words: "Open admin", "Publish <from> to <to>" (promote and deploy, with the environments' labels), "Back up now", "Restore a backup"; the engineering terms (release, revision, commit, drift, diff) stay on the detail pages of people with `deploy`. A button that a person's permissions do not allow is not shown at all. Every text goes through a message catalogue, with English and Persian (right to left) in the first version, chosen from the browser's language and changeable per person. Environments are named to people by their optional `label` in wpfleet.yaml, per language (`environments[].label.en` and `.fa`, at most 40 characters on one line), so a page says "Publish Preview to Live site" or "انتشار پیش‌نمایش در سایت اصلی" rather than mixing Latin config keys into a Persian sentence; a language without a label shows the name, and paths, the audit and the CLI always use the name. The labels are read from the fleet in the clone like the rest of it (`web.Environment.Label`, `Environment.In(lang)`), so a push changes them, and an action's steps name the environment in each viewer's language.

Server-rendered HTML from [templ](https://templ.guide) components, with [htmx](https://htmx.org) for partial updates; both are compiled into the binary and nothing loads from a CDN. Pages:

- **Your sites** (`/`): one card per site the person may see. A card names the site, links its live address ("View site", in a new tab), and lists the environments the person may see with a plain status from the readiness of the pods ("Online" when all are ready, "Starting" when some are, "Down" when none is; never an image tag), each with "Open admin" (a `POST` with the CSRF token, in a new tab) where the person has `login`. The environments are ordered live first and then back along the `promoteFrom` chain: the environment furthest from the start of its chain is the live one and carries a "Live" badge; when nothing promotes into anything, only a fleet of one environment has one, since the UI cannot tell which one visitors see. The card loads the last backup of its first environment in words after the page ("Backed up 3 hours ago", "Backups are off", or "Could not check the backups right now" when the cluster cannot be read, which must never read as backups being off). When an environment's `promoteFrom` runs another version and the person has `deploy` there and may see the source, the card offers "Publish <from> to <to>" for the environment closest to live, as a secondary link to a page that asks first (`GET /sites/{env}/{site}/promote`: which version goes where, that visitors see it at once when the target is live, "Publish now" as the one button that posts, and "Cancel"), so one click on a card never puts a new version on a site. Every card also has "Backups and more", a visible link to the site's page, and its name is styled as a link, since a touch screen has no hover to show it. With more than six sites a search box filters the cards by name or address: a plain `GET /?q=` form that htmx submits as the person types, swapping only the list and keeping the address in step. A person with no sites is told so and whom to ask. The brand's welcome text, when there is one, stands under the heading.
- **Site** (`/sites/{env}/{site}`): the status, the address, the last backup in words (when the cluster cannot be read, one line says so and the address and the backups show as unknown, not as missing or off) and links to the same site in the other environments the person may see; then the actions the person's permissions allow, each with one line on what it does: "Open admin", "View site", "Publish <from> to <env>" (only when the source runs another version; it leads to the same page that asks first), "Back up now" and "Restore a backup"; then the backups in words ("Yesterday at 03:12 UTC", the size of the content copy, until when it is kept). People with `deploy` also get "Technical details", a closed disclosure with the image, revision, commit, volume, "Deploy from Git", the pods, the release history (`SiteView.Releases`, `[]ui.ReleaseEntry`: revision, when, status, short commit, and the commit's Git author, so a publish from the UI shows who made it), what a deploy would change (with the drift as a badge) and the Git history of the site file; the diff and the file history load when it is opened. A site whose values turn backups off says so instead of an error when the bucket cannot be read, and still lists the backups taken before they were turned off.
- **Restore** (`/sites/{env}/{site}/restore`, `restore` only): what a restore replaces (the content and settings in the database; with the uploads, the files changed or deleted since the backup, while files uploaded after it stay), that it cannot be undone, the backups that have a database copy to choose from in words, and the site's name to type before it starts. The field turns off a phone's capitals and corrections, and the server compares the name without case or surrounding spaces (site names are DNS labels, so nothing else can match), since the name is there to make the person stop and read, not to test their typing. A name that does not match, or no backup chosen, brings the same page back with status 400, the error under the field it is about (`aria-invalid`, `aria-describedby`) and the backup, the uploads choice and the typed name kept. The warning that a restore cannot be undone is a paragraph with a warning border, never a badge, so it wraps on a phone.
- **Action:** deploy, publish, backup and restore show their steps in plain words as they come over server-sent events, with the Jobs' raw log in a closed disclosure. A step with engineering words has a plain form for everyone and the engineering one for people with `deploy` on the site: "Saving a copy of the content…" or "Putting the content back…" rather than the Job's name, "Reading the latest settings…" rather than Git, "The new version is published." rather than the commit, and "The site is updated." rather than the Helm revision. The result says what happened and what to do next (check the site; or try again and whom to ask), with a link back to the site. A failed action says what failed in the person's words (the deploy, the backup, reading Git, the server stopping); the error behind it is shown, closed, only to people with `deploy` and is always in the audit line.
- **Refusals and errors** say what happened in plain words, what the person can do (a refusal for want of a permission says to ask for access), and whom to ask: the brand's `supportURL` and `supportEmail` (see "Branding"; both optional), the same ones "Need help?" in the header leads to, else the person who set up the tool. That holds before sign-in too: a person the callback refuses for want of any access rule has no session and is told to ask their support team or the person who set up the tool, in the brand's words, never wpfleet's name or the identity provider's groups. A restore whose typed name did not match is not a refusal: the restore page comes back with the error under the field.

Numbers, dates and times on every page are written in the viewer's digits. Relative times ("3 hours ago") and days ("Yesterday at 03:12 UTC") are in the viewer's language; Persian dates are in the Solar Hijri calendar ("۶ آذر ۱۴۰۵"), English ones in the Gregorian, the technical tables of people with `deploy` included (`Lang.Time`: "27 Nov 2026 at 09:05 UTC", "۶ آذر ۱۴۰۵ ساعت ۰۹:۰۵ (UTC)"). Clock times are in UTC, since the server does not know the viewer's time zone. The pages use the shared `wf-*` classes of the stylesheet and page classes prefixed `wf-page-`; a status is always said in words and a sign as well as a color, every control has a label, and actions are buttons in forms while navigation is links.

`internal/infra/web` serves `GET /` (your sites, `?q=` to search), `GET /auth/signin` (the sign-in page, where a request without a session is sent; its button starts the sign-in at `/auth/login`), the brand's files `GET /brand/logo`, `/brand/favicon` (also `/favicon.ico`) and `/brand/theme.css` (see "Branding"), `GET /sites/{env}/{site}` and its fragments `status` (the last backup, for a card), `diff`, `history` and `backups`, which htmx loads after the page so a slow cluster does not hold it back; `GET /sites/{env}/{site}/restore` and `GET /sites/{env}/{site}/promote` (the page that asks before a publish); the actions as `POST /sites/{env}/{site}/deploy`, `promote`, `admin`, `backup` and `restore`; `GET /tasks/{id}` and `GET /events?task={id}` for an action's progress, which anyone who may view the site may follow, each in their own language; `POST /lang`, which stores the person's language in the session; `/auth/login`, `/auth/callback` and `POST /auth/logout`; `POST /hooks/git`; `/healthz`, and `/readyz`, which answers once the clone has a commit; and `/metrics` on a handler of its own. A deploy from the UI syncs the clone first and waits for readiness; a promote syncs the clone, then plans on that commit (the snapshot can be a poll interval old), commits only when the image changes, and deploys the commit either way. When the branch moves between the plan and the commit, a promotion someone else already pushed deploys their commit, and a source that moved again fails the action without a commit, so a commit message never names a version other than the one it sets. A request without a session is sent to the sign-in page and, after the provider, back, and a refusal is checked before the site's existence, so it says nothing about which sites exist. The package defines the small interfaces it consumes (`Authenticator`, `Sessions`, `Authorizer` with `Any` for the sign-in, `Repo`, `Operations` with `History`, `Locker` with `Blocking` and `Auditor`) in the types of the real packages (`access.Identity` and `access.Permission`, `session.Session` and `session.Flow`, `gitrepo.Signature`, `gitrepo.Edit` and `gitrepo.LogEntry`, `audit.Record`), so its tests run on fakes while `*session.Manager`, `access.Policy` and `*oidc.Provider` satisfy them as they are; `web.FleetOps` is the `Operations` over `internal/ops` on a directory, and `(*web.Server).TriggerSync` lets the poll loop use the webhook's syncer. It was first built with copies of those types, because the packages did not exist yet; they went when the parts merged. The sign-in flow takes its state, nonce and verifier from `session.NewFlow` and checks return paths with `session.SafeReturnPath`, so that logic lives in one place. Every response carries a Content-Security-Policy that allows only the server's own scripts, styles, fonts, images and streams; htmx, its server-sent events extension and the Persian font are vendored under `internal/infra/web/ui/static` with their versions and licenses, and the Go that templ generates is committed (`just generate`, checked in CI).

### Branding

The server is meant to be run by a client for its own people, so it carries the client's name, logo and color rather than wpfleet's: a person signs in to "Northwind Media", not to a tool they have never heard of. The look is set in `server.branding` of the server's `wpfleet.yaml`; the image files live in the client's own fleet repository, next to its sites, so changing the logo is a commit like any other and needs no new image or release of wpfleet.

```yaml
server:
  branding:
    name: Northwind Media              # default wpfleet
    logo: brand/northwind.svg          # a path inside the fleet repository
    logoIncludesName: false            # true for a wordmark: no name printed beside it
    favicon: brand/favicon.png         # default: wpfleet's own
    primaryColor: "#0e7c66"            # default #1f5fbf
    supportURL: https://help.example.com/wordpress
    supportEmail: web-help@example.com # used when supportURL is empty
    welcome:
      en: Open your site's dashboard from here.
      fa: داشبورد سایت خود را از اینجا باز کنید.
```

- **What is checked when.** `Config.Validate` checks the section as text, in every fleet: a non-blank name; logo and favicon paths that are relative, stay inside the repository and end in `.png`, `.svg` or `.webp`; a logo whenever `logoIncludesName` is set, since the header would otherwise show no name at all; a CSS hex color (`#rgb` or `#rrggbb`); an absolute `http` or `https` support URL; a plain support address (`help@example.com`, not `Help <help@example.com>`); and welcome texts of at most 500 characters. `serve` then reads the two files from the clone and refuses to start when one is missing, larger than 512 KiB, a symbolic link out of the repository, or not what its extension says (the PNG and WebP signatures, `<svg` in the first KiB). After a push the files are read again from the new snapshot; a broken one is left out with a warning in the log (the name alone, wpfleet's favicon), so a bad commit never takes the pages down. `web.LoadBrandImage` is that one check, for both; `serve` passes the section to the web package as `web.Deps.Branding` (a `web.Branding` whose `Dir` is the newest snapshot) with `web.Deps.Version` for the footer.
- **Serving.** `/brand/logo`, `/brand/favicon` and `/brand/theme.css` need no session, since the sign-in page shows them. Each answers with an ETag (a hash of the file) and `304` to a matching `If-None-Match`. The pages link them with that hash in the query (`/brand/logo?v=<hash>`), and such a request is cached for a year (`immutable`), so a new logo is a new address; a request without the current hash, like a browser's `/favicon.ico`, is cached for an hour. wpfleet's own stylesheet is linked the same way (`/static/app.css?v=<hash>`, `ui.StylesheetURL`), so the pages of a new version never meet the stylesheet of an old one in a browser's cache. An SVG is served as `image/svg+xml` with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`, and the UI shows it only in `<img>`, where it runs no script either way.
- **Color.** The page's Content-Security-Policy allows no inline style, so the color reaches the page as `/brand/theme.css`, a stylesheet `internal/domain/brand` writes after `app.css`. It sets `--wf-primary`, `--wf-primary-contrast` and `--wf-link` for the light theme and, under `prefers-color-scheme: dark`, for the dark one. The text on a button is black or white, whichever contrasts more, which always reaches WCAG AA (4.5:1). Where the color itself is too light for the light theme's page or too dark for the dark one, it is darkened or lightened by the smallest step that gives a button's edge 3:1 and a link 4.5:1 against both the page and the cards. The page and card colors of `app.css` are the ones the code checks against, and a test keeps them equal.
- **The footer is not branding.** Every page, the sign-in, refusal and error pages included, ends with "Powered by wpfleet <version> · Apache-2.0 license · github.com/rahacloud/wpfleet", in the person's language, linking the repository and the license. No setting changes or hides it; a test renders it under a brand that tries.
- **The shell.** The header holds the logo and the name (a link home; with `logoIncludesName`, for a wordmark that already shows the name, the logo stands alone and the name stays in the link for screen readers only, on every page the sign-in page included, and comes back into view whenever the logo is left out), "Need help?" when a support URL or address is set, the person's name (their email on hover; on a phone only for screen readers, since beside the other links it pushed "Sign out" onto a third row of the header), the language switch and "Sign out". The switch is one button per other language, so choosing is one click; before sign-in, where there is no session to keep the choice in, it is a link that adds `?lang=` to the page (to the sign-in page from the pages after sign-out and after a failed sign-in, which a link cannot show again). A language picked on the sign-in page goes with its button to `/auth/login`, into the flow cookie (`session.Flow.Lang`), and the callback starts the session with it, so the person lands on the home page in the language they picked; the signed-out and failed sign-in pages keep the language too, and their link to sign in again carries it. The sign-in page says what the server is for in plain words and has one button, "Sign in with your company account"; the signed-out and failed sign-in pages lead back to it. The home page shows the welcome text in the person's language, the English one when theirs has none (marked with its own `lang` and `dir`, so a screen reader reads it with an English voice and its punctuation stays in place on a Persian page), and the empty state, the refusals, the error pages and a failed action name the same support contact as the header.
- **The design system.** `app.css` defines the tokens (`--wf-primary`, `--wf-primary-contrast`, `--wf-bg`, `--wf-surface`, `--wf-text`, `--wf-muted`, `--wf-radius`, and others prefixed `--wf-`) and the classes the pages use: `wf-btn` with `wf-btn-primary`, `wf-btn-secondary` and `wf-btn-danger`, `wf-card`, `wf-grid`, `wf-stack`, `wf-row`, `wf-badge` with `wf-badge-ok`, `wf-badge-warn` and `wf-badge-bad`, `wf-muted` and `wf-help`; a page's own classes are prefixed `wf-page-`. It uses logical properties only, so one stylesheet lays out both directions; follows `prefers-color-scheme`; gives every control a visible focus ring and a 44 px target; and fits a 360 px screen without scrolling sideways, a wide table scrolling inside its card instead. Persian text is set in Vazirmatn (SIL Open Font License, its Arabic-script subset only, vendored with its license); Latin text keeps the system font.

### Operations shared with the CLI

The logic of each command moves from `internal/cmd/<verb>` into `internal/ops`, as functions that take the environment, the sites and options and return typed results, with progress through a callback rather than a writer. The CLI commands become flag parsing and printing around them, and the server calls the same functions, so the two can never behave differently. One operation runs per site and environment at a time across the server; a second one is refused with the name of the action in progress.

### Running it

```text
internal/cmd/serve/        the serve command: flags, wiring, graceful shutdown
internal/ops/              deploy, diff, promote, admin, backup run/list/restore, as functions
internal/domain/access/    rules, permissions and their evaluation (pure)
internal/domain/audit/     the audit record (pure)
internal/infra/gitrepo/    clone, fetch, hard reset, commit and push with go-git
internal/infra/oidc/       discovery, the code flow with PKCE, ID token verification
internal/infra/session/    the encrypted session cookie and CSRF tokens
internal/infra/web/        echo routes, handlers, server-sent events, /healthz, /readyz, /metrics
internal/infra/web/ui/     templ components and the embedded static files (htmx, CSS)
deployments/helm/wpfleet/  the chart that runs the server
build/package/Dockerfile   the image: the static binary on a distroless base, as a non-root user
```

`wpfleet.yaml` gains a `server` section:

```yaml
server:
  listen: ":8080"
  metricsListen: ":9090"
  publicURL: https://wpfleet.example.com   # the OIDC redirect is <publicURL>/auth/callback
  git:
    url: git@github.com:example/fleet.git
    branch: main
    pollInterval: 1m
    committer: {name: wpfleet, email: wpfleet@example.com}
  oidc:
    issuer: https://sso.example.com/realms/main
    clientID: wpfleet                       # the secret comes from WPFLEET_OIDC_CLIENT_SECRET
    groupsClaim: groups
    scopes: []                              # empty: openid, email, profile, and groups if advertised
    assumeEmailVerified: false              # keep an email that has no email_verified
  session:
    maxAge: 8h
  admin:
    matchEmail: true
  access:
    - group: platform
      environments: ["*"]
      sites: ["*"]
      allow: [view, deploy, login, backup, restore]
    - group: shop-team
      environments: [development, staging]
      sites: [shop]
      allow: [view, login]
  branding:                                 # see "Branding"
    name: wpfleet
    logo: ""                                # a PNG, SVG or WebP file in the fleet repository
    primaryColor: "#1f5fbf"
```

In the cluster, an environment with an empty `kubeconfig` uses the pod's ServiceAccount. The chart in `deployments/helm/wpfleet` makes the Deployment (one replica, because pushes and the per-site locks are in memory), the Service, the Ingress with its TLS secret, the ServiceAccount, and a Role with its RoleBinding in each site namespace listed in its values, since a tenant often holds only namespace admin and cannot make a ClusterRole. The Role allows what Helm and the operations touch there: Secrets, ConfigMaps, Services, PersistentVolumeClaims, Deployments, Ingresses, CronJobs, Jobs, Pods (read only: the chart makes them through Deployments and Jobs, and the right to create one would run it as any ServiceAccount of the namespace) with `exec` and `log`, ReplicaSets (read only: Helm's wait computes a Deployment's status from them, and without them every deploy from the UI, which waits for readiness, stays `Unknown` until it times out), and Events. The OIDC client secret, the session key, the Git credentials and the S3 keys come from one Secret made by hand. The Deployment uses the `Recreate` strategy, so a rollout never runs two servers at once; the container runs as user 65532 with a read-only root filesystem, the data directory (`/var/lib/wpfleet`: the clone in `fleet/`, its snapshots in `snapshots/`), wp-cli's cache (`XDG_CACHE_HOME=/var/cache/wpfleet`) and `/tmp` on emptyDirs, and probes on `/healthz` (liveness and startup) and `/readyz`. The server's `wpfleet.yaml` comes from the chart's `config` value through a ConfigMap mounted at `/etc/wpfleet/wpfleet.yaml`, with `server.listen` and `server.metricsListen` set from the chart's ports; the container's arguments default to `serve --config /etc/wpfleet/wpfleet.yaml --data /var/lib/wpfleet --shutdown-timeout 5m`, and `terminationGracePeriodSeconds` (330) leaves the stop that long to finish. The Secret (`existingSecret`) holds each secret under its variable's name, `WPFLEET_SESSION_KEY` required and the others optional; with `git.sshKey.enabled` its deploy key and `known_hosts` keys are mounted as files that `WPFLEET_GIT_SSH_KEY` and `SSH_KNOWN_HOSTS` name, since go-git checks host keys and an SSH clone without them fails. `rbac.extraRules` adds rules for a fleet whose own chart makes other kinds; the embedded chart's HorizontalPodAutoscaler and PodDisruptionBudget only render with more than one replica, which a ReadWriteOnce uploads volume refuses, so the Role leaves them out. The image (`build/package/Dockerfile`, `just image`) builds a static binary with `CGO_ENABLED=0` on `golang:1.27-alpine` and copies it onto `gcr.io/distroless/static-debian13:nonroot`, which has CA certificates and time zones and no shell. Its build context has no `.git`, so Go records no commit there; the build arguments `VERSION` and `COMMIT` (which `just image` takes from `git describe` and `git rev-parse`, and CI from the pushed commit) are stamped with `-X` into `internal/infra/version`, whose `Short()` prefers them over versioninfo's reading of the build info and leaves out the commit when the version already names it, as `git describe --always` does without a tag (`8c38585`) and after one (`v0.1.0-3-g8c38585`). versioninfo sets its own variables from the build info when the program starts, so a `-X` on them would be overwritten. GoReleaser stamps the release binaries the same way, and CI checks that the image's `--version` names its commit.

### The serve command

`internal/cmd/serve` wires the packages together; the build differs from the plan above in these ways, each for the reason given.

- **Two files, two jobs.** `--config` (or `WPFLEET_CONFIG`) is the server's own `wpfleet.yaml`: its `server` section, and the environments only so `server.access` can be checked when it loads. It cannot live in the fleet repository, because it names that repository. The fleet itself (environments, kubeconfigs, chart, registry, bucket) is read from the clone on every request, so a push changes what the server does without a restart. At start the server refuses a rule that names an environment the clone's fleet does not have, since such a rule never matches and silently hides sites.
- **It refuses to start** without a valid server section (`ValidateServer`: listen address, public URL, repository, committer, OIDC issuer and client), without `WPFLEET_SESSION_KEY`, without at least one access rule, with a rule `access.Policy.Validate` refuses (an unknown permission name among them, which `config` does not check), or when the fleet in the clone does not load.
- **Snapshots, not the clone.** `gitrepo.Sync` hard-resets the clone in place, and an operation reading the fleet during a reset could see half of two commits. So after every sync and commit the server copies the head's tree, without `.git`, into `<data>/snapshots/<sha>`, and every read and every operation loads the fleet from the newest snapshot. An operation that started on an older snapshot keeps reading consistent files; a replaced snapshot is deleted an hour later, and the snapshots of an earlier run at start. Only promote's edit works in the clone itself, inside `Repo.Commit`'s lock. Reading the newest snapshot's path never waits for a sync or a commit, which hold the clone's lock through the fetch or the push: every page reads it for the brand's images, the sign-in page and the favicon included, so a slow remote must not hold them back. A deploy still runs on the newest snapshot rather than on exactly the commit the UI synced to, so a push in the moment between the two deploys the newer commit while the release description names the older one; the next deploy corrects it.
- **Groups are trimmed at sign-in** to the groups some rule names. Other groups can grant nothing, and a person in hundreds of groups would push the session cookie past the 4 KiB a browser keeps.
- **Sync** is the webhook's coalescing syncer for both triggers: the poll loop calls `TriggerSync` every `server.git.pollInterval`, so a poll and a webhook never sync at once. Without `WPFLEET_GIT_WEBHOOK_SECRET`, `/hooks/git` answers 404 and only polling syncs.
- **Cookies** are `Secure` and `__Host-` prefixed when `server.publicURL` is `https`; a plain `http` public URL, for a local test, gets cookies without them, since a browser would drop them otherwise.
- **Logs** are JSON on stdout at info level (debug with `--verbose`), audit lines among them; `/metrics` is on `server.metricsListen` and the UI listener does not serve it. The HTTP servers have header and read timeouts but no write timeout, because an action's progress streams for as long as it runs.
- **Stopping** (SIGTERM) closes the listeners, then waits up to `--shutdown-timeout` (5 minutes) for running actions and syncs, then for the Events in flight. Past the timeout it cancels the actions and waits up to ten seconds more for each to write its `failed` line; after that the auditor still writes lines but starts no new Event, since an Event started while the server waits for them could be lost or misuse the wait group. A deploy cut short leaves its Helm release pending, so the timeout is long and the chart's grace period longer.

## Not in the first version

An operator with a `WordPressSite` resource, image builds inside the cluster (BuildKit or Kaniko), plugin vulnerability reports, restore tests on a schedule, and in the server: pull requests instead of pushes, `build`, `copy`, and more than one replica. The CLI came first so that its model could settle; the server is a second front end on the same operations, not a new model. [ROADMAP.md](ROADMAP.md) says which of these are planned and when: the vulnerability report comes first, scheduled restore tests and pull requests instead of pushes (as two-person publishing) next, and the operator, builds inside the cluster, and `build` and `copy` in the server later. More than one replica is not planned, for the reason it gives.
